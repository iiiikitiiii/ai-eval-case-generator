# 《交互体验优化需求》技术评估

评估对象：`doc/交互体验优化需求.md`。以下每一条都对照当前代码库实际状态核实过（不是凭印象判断），标注了"现状核实"的地方都是直接读代码/查表结构确认的。

## 总体判断

需求整体合理，不触碰 Agent 医学判断逻辑和六阶段旅程模型，跟"非目标"里说的一致，技术上不冲突。

但工作量比文档表面看起来大，因为好几条需求依赖的是**目前完全没有的基础设施**，不是每条各自独立的小改动：

1. **操作留痕/审计**——目前只有 `ReviewFlag`/`BoundaryDecision`/`MockEntry`/`Query` 各自有 `decided_by`/`resolved_by` 字段，但 `PipelineRun`（运行记录）和 `RegressionRun`（回归结果）完全没有"谁做的"这个概念。`AuditLog` 表（`backend/app/db/models/audit.py`）早期就建好了，字段设计正好能用（`actor_id`/`action`/`before`/`after`），但检查下来**从未被任何代码实际写入过一条记录**——一直是个空表。P0#1（执行人）、P2#2（切换审计）都要用到这个能力，建议一次搭好，别为每条需求各写一套。
2. **批量操作**——目前所有裁定类操作（flag/boundary/mock/query）都是逐条 `PATCH`，没有一个是批量的。P1#3 明确要批量，做的时候应该设计成可复用模式，不是只为 query 单独写一次。
3. **列表筛选/搜索**——board 的用例库 tab 已经有一套成熟的筛选器模式（filter state + querystring），P1#2 的病例队列筛选可以照搬这个模式，不用重新设计。

## 逐条评估

### P0-1：发布前回归状态必须与实际规则一致

**现状核实**：`agent_service.publish_version()`（`backend/app/services/agent_service.py:67`）没有任何门禁检查——只是把目标版本状态改成 `published`、旧版本归档，直接提交。但前端文案（`PromptsPage.tsx:333`）写的是"发布前的门禁"。点发布按钮，不管有没有跑过回归、跑没跑通，都会立刻生效。文档描述的问题完全属实。

**技术方案**：
- 方案 1（强制门禁）：`publish_version()` 里查该版本关联的最近一次 `RegressionRun`，无 PASS 记录时拒绝（400），无回归用例的 Agent 走"未配置门禁，需显式确认"分支——后端要新增一个跳过确认的参数。
- 方案 2（软提示）：后端不变，只改前端——发布前弹窗展示最近回归结果，未通过/未跑过时要求勾选确认才能继续。
- 列表展示"最近回归时间/结果/执行人"：时间和结果 `RegressionRun` 已有，"执行人"没有——需要给 `RegressionRun` 加 `triggered_by` 外键（小 migration）。

**复杂度**：方案 2（推荐先做）小；方案 1 中，因为要处理"未配置回归用例的 Agent"这个边界分支。

**开工前需要产品决定**：选哪个方案——这决定了要不要真的拒绝发布，影响面完全不同，我不能替产品做这个判断。

### P0-2：阶段分析失败可局部恢复

**现状核实**：`CaseWizardPage.tsx:422` 的判断条件是 `caseDetail.stage_map.length === 0`——B 一旦成功过，`stage_map` 就不再是空的，"运行阶段映射 + 组合抽取"这个按钮直接消失，没有任何入口能单独重跑 C。后端 `POST /cases/{id}/pipeline/run-b`、`run-c` 本身是两个独立 endpoint，技术上早就支持单独调用，只是前端从没暴露过"只点 C"的按钮——这是一个纯粹的前端遗漏，不是架构限制。

**技术方案**：把按钮拆成两个独立入口，判断条件从 `stage_map.length` 改成分别读 B、C 各自最近一次 `PipelineRun` 的状态。这个数据工坊页面目前没有直接引用（`TracePage` 有），需要在 `CaseWizardPage` 里加一次 `getPipelineRuns` 调用。纯前端改动，后端不用动。

**复杂度**：中——不是因为技术难，是因为验收标准里那句"重试局部步骤不会覆盖已经人工裁定的边界判断"牵出一个既有行为问题：查了 `agent_b.py`（第 69-71 行），**Agent B 每次重跑都会把 `boundary_decisions` 全部删除重建**，这是当前就有的幂等重跑设计，不是这次要改的范围。但这次需求第一次真正给用户暴露"重试 B"这个操作入口，用户点了会发现已裁定的边界判断被清空——这不违反需求本身写的验收标准（那句话说的是"重试局部步骤"，字面上可以理解为只重试 C 不受影响），但会是用户第一次真实撞见的行为，需要在开工前想清楚要不要顺带解决。

**开工前需要产品决定**：重试 Agent B 本身（不是 C 失败去重试 C，是 B 结果本身要改判去重跑 B）时，要不要保留已经人工裁定的边界？现状是全清空重来。

### P1-1：重构"产出"页为可阅读的测试资产预览

**现状核实**：`CaseWizardPage.tsx` 的 `'out'` 步骤目前是 `<pre>{JSON.stringify(exportData.test_cases, ...)}}</pre>`，纯 JSON，跟文档描述一致。但——**`QueryCard` 组件已经存在**（`shared/ui/QueryCard.tsx`，上一轮做用例库详情弹窗时抽出来的），本身就是"测试方向/实际 query/预期要点/红线关注/资料/画像脚本"的完整可读卡片渲染，`readOnly` 模式已经现成。

**技术方案**：`'out'` 步骤直接换成遍历 `caseDetail.cutpoints` 渲染 accepted 的 query，每条用 `<QueryCard readOnly .../>`；上方摘要统计（按阶段/场景/来源分布）在前端对已有数据 `reduce` 就行，不需要新接口；原始 JSON 挪进 `<details>` 折叠区；导出按钮已经有（Excel/ZIP/JSON 三个都在），不用动。

**复杂度**：小——这批需求里现有基础设施复用度最高的一条，零后端改动，前端工作量也小，而且用户能立刻感受到差异。**建议排在最前面做**，见下面的顺序建议。

### P1-2：病例队列支持日常检索与优先级处理

**现状核实**：`CaseListPage.tsx` 确认没有搜索框、没有状态筛选下拉、没有"当前待办/最近失败步骤"列；新建表单字段是姓名/性别/年龄/诊断/医院（真实患者字段），没有"病例别名"这个概念。

**技术方案**：
- 搜索、状态筛选：病例量级不大，前端本地过滤就够，不需要新后端接口。
- "当前待办/最近失败步骤"：`CaseListItem` 需要后端补充字段（比如 `last_failed_agent: str | None`），`list_cases()` 里要为每个 case 额外查一次最近失败的 `PipelineRun`——量级小的话没问题，但要注意别写成 N+1 查询（用一次批量查询建 lookup，不要在循环里逐个查）。
- "病例别名"：`patient_meta` 是 `dict[str, Any]`（JSONB），技术上直接加一个 `alias` 键即可，不需要动 schema；前端新建表单加一个输入框，列表展示 `alias || case_no`。

**复杂度**：中——主要是"最近失败步骤"的后端聚合要写对，性能上要留意。

**开工前需要产品决定**：病例别名要不要唯一性约束？允许重复吗？（这期没有跨病例引用，可以先不管这个）

### P1-3：用例审核支持批量操作，并使用业务语言

**现状核实**：`PATCH /cases/{id}/queries/{query_id}` 只支持单条改一个；前端按钮文案确实是"纳入 / 引用"（`CaseWizardPage.tsx`），"引用"作为拒绝的说法确实不直观，这是我自己在早前几轮构建时留下的措辞问题，文档指出得对。另外确认了一点文档没直接说但相关的事实：工坊页面 `QueryCard` 里 `scenario_type` 目前**直接显示 `SCN17` 这样的 code，没有配对场景中文名**——虽然看板那边（`board_service.build_query_export_dict`、Excel 导出）已经把 `scenario_name` 加上了，但那是走 dict 手工构造；工坊这边 `CaseDetail` 是 `Pydantic.model_validate(case)` 直接从 ORM 序列化，`Query.scenario_type` 是纯字符串、不是外键，没有 relationship 可以顺带带出名字，这个字段要单独想办法补（不是加一行代码就完事，属于这条需求里一个真实的小复杂点）。

**技术方案**：
- 批量接口：新增 `PATCH /cases/{id}/queries/batch`，body 带一组 `query_id` + `decision`（+ 可选 `reason`，`Query` 模型要加 `decision_reason: str | None` 列，小 migration）。
- 前端：用例列表加勾选框 + 筛选（场景/阶段/来源/审核状态）+ 批量操作条，筛选 UI 可以照搬 board 用例库 tab 那一套。
- 文案：全局把"引用"替换成"不纳入"。
- `scenario_name`：给 `CaseDetail` 序列化补一步——在 `_to_detail()` 里跟处理 `flags`/`persona`/`mocks` 一样，对 `cutpoints` 下每个 `query` 后处理填充 `scenario_name`（查一次 `ScenarioType` 建 code→name 的 lookup，不是每条都查一次库）。

**复杂度**：中大——批量接口 + 筛选 UI 是主要工作量；`scenario_name` 这块虽然小但容易漏掉，需要显式排进任务里。

### P1-4：资料导入前支持整理与确认

**现状核实**：上传前预览、上传后缩略图已经有（上上轮做的）。但**没有删除已上传但未抽取资料的能力**——后端没有对应 endpoint，`case_service.py` 没有对应函数，`core/storage.py` 目前只有 `put_object`/`get_object_bytes`/`presigned_url`，**没有 `delete_object`**。运行按钮现在点了就直接跑，没有"确认使用 N 份"这一步。

**技术方案**：
- 后端：`core/storage.py` 加 `delete_object(key)`；新增 `DELETE /cases/{id}/documents/{document_id}`，只允许 `case.current_step == 'up'`（还没运行过 Agent A）时删除，同步删 MinIO 对象。
- 删除后剩余文档要不要重新编号 `seq`？如果不重编号会跳号（1、3、4）。这个阶段还没有其他表引用这些 `seq`，重编号风险可控，但是个需要显式决定的产品问题，不是我能替产品定的技术细节。
- 前端：卡片加删除按钮 + 二次确认；运行按钮改成"确认使用 N 份运行"的二次确认。

**复杂度**：中——删除 MinIO 对象、`seq` 处理需要想清楚，技术本身不难。

**开工前需要产品决定**：删除后剩余单据的 `seq` 要不要重新编号？

### P2-1：让覆盖空白可行动

**现状核实**：`CoverageMatrix`（`BoardPage.tsx`）纯展示，格子无点击。

**技术方案**：
- 跳转到"已筛选的用例库"：同页面内 tab 切换 + 传 filter state，纯前端，简单。
- 跳转到"适合补测的病例队列"：**这是这批需求里唯一真正需要新设计业务逻辑的地方**——覆盖空白格只有 `(journey_stage, scenario_type)` 两个维度，"哪些病例适合补这个场景"目前系统没有这个反向索引概念。我的候选定义：找 `stage_map` 里该 `journey_stage` 状态为 `covered` 或 `real_gap`、且这个病例在该场景下还没有 accepted query 的病例——这是我给的一个合理方案，不是唯一答案，需要产品确认是否符合预期。
- "创建补测任务草稿"：文档自己说了"本期不做任务系统，可先复制补测清单"，可以先做成"复制一段文字到剪贴板"，不需要建任务系统。

**复杂度**：中——候选病例查询逻辑需要新写，但病例量级小（几十到未来几百），不用担心性能。

**开工前需要产品决定**："适合补测的病例"的判定规则是否符合预期（见上面的候选定义）。

### P2-2：全局模型切换明确影响范围并留痕

**现状核实**：`AppSetting` 是纯 key-value 单行表（`key`/`value` 两列），没有历史记录概念，切换是乐观更新，没有确认弹窗。`PipelineRun` 本身没有 `triggered_by` 字段——"谁在什么时候把全局设置从 A 切到 B"目前完全没有留痕能力。但每次运行**实际用的**模型有记录（`PipelineRun.token_usage.provider`，上一轮加的），只是"谁切换的全局默认值"这件事没有单独记录。

**技术方案**：`settings_service.set_llm_provider()` 里除了更新 `AppSetting`，顺带写一条 `AuditLog`（`action="llm_provider.switch"`, `before`=旧值, `after`=新值, `actor_id`=当前用户）——**这条需求刚好是 `AuditLog` 这张空表第一次被真正用上**，不用新建表结构。前端切换前加确认弹窗，切换后 toast 提示，设置页或运行记录页新增一个读取 `AuditLog` 按 `action` 过滤的列表。

**复杂度**：小中——这条反而是全部需求里最顺的一条，因为存储结构已经现成，只是从来没人用过。

## 对"建议实施顺序"的评估

文档第 6 节给的顺序：第一阶段（发布规则、B/C 局部重试、产出页预览）→ 第二阶段（病例检索、批量审核、资料整理）→ 第三阶段（覆盖空白、模型切换审计）。

整体合理，但有两点建议调整：

1. **产出页改用例预览应该排全部需求最前面**——零后端改动、直接复用现成的 `QueryCard`、用户能立刻感受到差异，性价比在这批需求里最高，适合作为验证方向的第一件事。
2. **模型切换审计不必等到第三阶段**——它依赖的 `AuditLog` 表已经建好、逻辑跟其他功能没有耦合，可以提前跟"发布规则一致化"放在第一阶段一起做：两者本质上是同一类工作（给已有机制补留痕），一起做还能顺带验证 `AuditLog` 这张表真的好用，为后面其他需求要用到留痕的地方（P0-1 的"执行人"、P1-2 的"最近失败步骤"）打个样。
3. **批量审核建议排在"资料整理"之前**——批量审核直接命中"体验人员 30 秒判断"这个文档写的核心目标，资料整理解决的是导入环节的错误预防，重要但不如批量审核跟主目标贴得紧。
