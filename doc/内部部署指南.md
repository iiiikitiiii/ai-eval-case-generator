# 内部部署指南

这份指南对应 `infra/docker-compose.prod.yml`——跟本地开发用的
`infra/docker-compose.yml` 是两份完全独立的配置，不要混用。生产版本做了
这几件事，都是这次打包时针对"内部部署给团队用"这个场景改的，不是照抄
开发配置：

- Postgres / Redis / MinIO 不对外暴露端口，只在容器内部网络里被
  backend/worker 访问——服务器上除了部署这套东西的人，别人拿不到数据库
  连接串。
- 前端不再是 `vite dev` 开发服务器，是 `vite build` 出的静态文件由 nginx
  发布；nginx 同时把 `/api/*` 反代到 backend 容器——对外只需要开一个
  端口，不用分别管理前端和后端两个端口，也不用处理跨域。
- 代码是 build 时打进镜像的，不是挂载宿主机源码目录——生产环境不该有
  "改一下文件线上行为就变了"这种隐式联动，更新必须走"重新 build + up"
  这一个动作。
- 所有密码/密钥必须通过 `infra/.env.prod` 提供，compose 文件里没有任何
  默认弱密码兜底——不填就直接拒绝启动。

全流程（构建镜像、起容器、跑迁移、种子数据、真实登录、真实取数据）在写
这份指南时完整跑通过一遍，不是照着配置文件推测出来的步骤。

## 1. 前置条件

部署机器上需要：

- Docker（含 Compose v2，`docker compose version` 能正常输出）
- 能访问这个仓库的代码（`git clone`，或者把整个项目目录拷过去）
- 如果机器不能直接访问 MiniMax/Kimi/Anthropic 的 API：至少要能访问你
  实际要用的那个模型供应商的域名，这是 Agent 流水线能不能跑起来的
  硬需求，跟部署本身无关

## 2. 配置密钥

```bash
cd infra
cp .env.prod.example .env.prod
```

编辑 `infra/.env.prod`，至少要改这几项（`.env.prod.example` 里标了
"请改成…" 的都不能保留原样）：

- `POSTGRES_PASSWORD`、`S3_SECRET_KEY`：真实强密码，`S3_SECRET_KEY`
  MinIO 硬性要求至少 8 位。
- `JWT_SECRET`：一段随机长字符串，例如 `openssl rand -hex 32` 生成一个。
- `MINIMAX_API_KEY` / `KIMI_API_KEY`（至少填一个，看你们实际用哪家）。
- `HTTP_PORT`：团队访问这个系统要用的端口，默认 80（需要机器上有权限
  绑定特权端口；不方便的话改成比如 8080）。

`infra/.env.prod` 不要提交到 git——`.gitignore` 已经排除了所有 `.env`/
`.env.*` 变体（`.env.example`/`.env.prod.example` 这类模板文件除外，
这两份本来就该被提交，好让别人知道要填哪些字段）。这条排除规则是打包
这次部署顺手补的：这个仓库目前还没有 `git init` 过，之前 `backend/.env`
（本地开发用的真实密钥文件）完全没在排除名单里，一旦真的初始化 git 走
正常提交流程，密钥就会被直接提交进历史——这次一并修掉，不是这份部署
指南单独需要的东西。

## 3. 构建并启动

```bash
cd infra
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

**注意 `--env-file .env.prod` 这个参数不能省**——Compose 默认只会自动加载
名叫 `.env` 的文件用于配置文件里 `${VAR}` 这种插值，这份生产配置故意叫
`.env.prod`（避免跟本地开发那份 `.env` 混淆、不小心拿开发弱密码去部署），
所以每次跑 `docker compose` 命令都要带上这个参数。嫌麻烦可以设个 alias：

```bash
alias dcp='docker compose -f docker-compose.prod.yml --env-file .env.prod'
```

首次启动会顺序拉镜像、build backend/frontend、起 postgres/redis/minio
并等它们健康、backend 容器内自动跑 `alembic upgrade head` 建表、最后起
backend/worker/frontend。全部起来后 `dcp ps` 应该五个服务都是
`Up`/`healthy`。

## 4. 首次部署必做：建管理员账号 + 种子数据

这几步只需要在**全新数据库**上做一次，不是每次重启都要跑（种子脚本大多
是"已存在就跳过"，重复跑不会出错，但没必要每次都跑）。

```bash
cd infra

# 4.1 建第一个管理员账号，用来登录系统
dcp exec backend python -m app.seed \
  --email you@yourcompany.com --name "你的名字" --password "改成真实密码"

# 4.2 种子 Agent（A/B/C/D/F/S0 六个 agent 各自的 v1 版本 prompt）
dcp exec backend python -m app.seed_agents

# 4.3 种子用户画像库（4 个固定候选：患者/家属 × 低/较高认知）
dcp exec backend python -m app.seed_personas

# 4.4 导入业务方真实场景库（49 个真实场景 + 评分标准 + 红线目录）——
#     这份 xlsx 在仓库的 doc/ 目录下，不在 backend 镜像的构建上下文里
#     （镜像刻意只打包 backend/，不带业务方文档），需要先拷进容器：
dcp cp "../doc/专病管家测评标准-场景清单+标准.xlsx" backend:/tmp/scenarios.xlsx
dcp exec backend python -m app.import_scenario_standards /tmp/scenarios.xlsx
```

4.4 执行完应该看到：

```text
场景清单（六阶段）：49 条
评分标准：20 条
法规依据：7 条
通用红线：11 条
标准卡评分档：20 条
```

做完这四步，打开 `http://<部署机器地址>:<HTTP_PORT>`，用 4.1 建的账号
应该能正常登录，病例工坊/Prompt 后台/用例看板三个页面都能打开。

## 5. 更新部署（代码有新版本时）

```bash
cd infra
git pull   # 或者你们拉代码的方式
dcp up -d --build
```

这条命令会重新 build 有变化的镜像、重启对应容器，postgres/redis/minio
的数据卷不受影响。`alembic upgrade head` 每次容器启动都会自动跑一次，
新迁移会自动应用。

**这一步之后一定要确认 worker 真的重启了**——这是这个项目开发过程中
反复踩过的坑：backend 用 uvicorn 起，容器重建了代码就生效；但如果你用
的是别的编排方式让 worker 单独长期运行而没有真的重建容器，worker 进程
可能还在跑更新前的旧代码，行为对不上新代码却没有任何报错提示。用
`docker compose up -d --build` 这种方式部署，`up` 本身就会重建所有代码
变了的容器（含 worker），不存在"漏更新 worker"这个问题，但如果你们后续
换成别的编排方式（比如手动 `docker restart` 某个容器），一定要确认
backend 和 worker 两个容器都真的用了新镜像重启，不是只重启了一个。

## 6. 备份

需要备份的只有两个数据卷：

- `case-pipeline-hub_pgdata`——病例、用例、Prompt 版本、审计日志等
  全部结构化数据。
- `case-pipeline-hub_minio-data`——病历图片原始文件。

```bash
# Postgres：用 pg_dump，不要直接打包卷文件（容器运行中卷文件不是
# 一致性快照）
dcp exec postgres pg_dump -U caseflow caseflow > backup-$(date +%Y%m%d).sql

# MinIO：容器运行中可以直接打包卷目录（对象存储没有 Postgres 那种
# WAL/一致性问题），或者用 mc mirror 导出
docker run --rm -v case-pipeline-hub_minio-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/minio-backup-$(date +%Y%m%d).tar.gz -C /data .
```

## 7. 排查

```bash
cd infra
dcp ps                       # 五个服务的状态/健康检查
dcp logs backend --tail 100  # 某个服务的日志
dcp logs worker --tail 100
dcp exec backend python -c "from app.core.config import get_settings; print(get_settings().llm_provider)"  # 确认配置真的生效了
```

常见问题：

- **backend 容器一直重启/unhealthy**：多半是数据库还没准备好或者
  `DATABASE_URL` 拼错——看 `dcp logs backend`，entrypoint 里的
  `alembic upgrade head` 失败会直接把原始报错打出来。
- **登录一直 401**：确认 4.1 的账号真的建成功了（`已创建 admin 账号`
  这行输出），密码打错了直接改用 `docker exec` 进容器手动跑一遍
  `app.seed`（同一个邮箱地址会提示"已存在，跳过"，需要先在数据库里删掉
  这条 `users` 记录或者换个邮箱重建）。
- **上传图片/跑 Agent 一直卡着不动**：先确认 `worker` 容器是 `Up`（不是
  `Exited`）；再看 `dcp logs worker` 有没有真的收到任务、有没有报
  LLM API key 相关的错误。
- **改了 Prompt/代码之后行为没变**：参考第 5 节——确认 worker 真的用
  新镜像重启过，这是这个项目最容易踩的坑，务必先排除这个可能性再去
  查别的。

## 8. 没有外网/离线环境部署

如果部署机器完全没有公共互联网访问（内网隔离），在一台能访问外网的机器
上跑这一个脚本就能产出完整的离线部署包，不用手工重复 build/save 这些
步骤：

```bash
# 在能联网的机器上，仓库根目录下
./infra/build-offline-package.sh
```

这个脚本会自动 build backend/frontend 生产镜像、拉好 postgres/redis/minio
三个官方镜像、把全部镜像 `docker save` 压缩打包、连同 `infra/`（compose
配置 + 密钥模板）、`doc/`（含这份指南和业务方场景库 xlsx）、完整源码一起
打成 `dist/case-pipeline-hub-offline-deploy.tar.gz`，脚本自己也会验证一遍
"分片能拼回去、校验和对得上"再退出。

产出两种交付形态，都在 `dist/` 下：

- **单文件**：`dist/case-pipeline-hub-offline-deploy.tar.gz`（约 300MB）——
  不受传输大小限制时用这个最简单，U盘/内网文件服务器直接拷走。
- **分片**：`dist/parts/` 下每片默认 90MB（很多内网传输渠道/邮件系统卡在
  100MB，留了安全余量），适合传输渠道有单文件大小限制的场景。改分片大小：
  `SPLIT_SIZE=45m ./infra/build-offline-package.sh`。

分片这一份把 `dist/parts/` 整个目录（含 `.part-*`、`.sha256`、
`reassemble.sh`）传到目标机器后，在这个目录下执行：

```bash
./reassemble.sh   # 拼接分片 + 校验 sha256，失败会报错，不会静默产出一个损坏的文件
tar xzf case-pipeline-hub-offline-deploy.tar.gz
cd case-pipeline-hub-offline-deploy
./load-images.sh
```

之后就是本指南第 2 节开始的正常流程（配置密钥、启动、首次部署种子数据）。

目标机器仍然需要能访问你实际使用的 LLM 供应商域名——这是 Agent 流水线本身的需求，任何部署方式
都绕不开。
