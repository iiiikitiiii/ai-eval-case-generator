# 病例流水线中枢：测试用例体验优化需求

## 1. 背景

当前系统已具备从病例资料导入、Agent 辅助生成、人工复核到测试用例导出的完整链路。实际界面走查显示，主流程与人工关卡已较清晰，但测试体验人员在**检索工作、阅读产出、批量审核和维护版本**时，仍需理解较多工程字段或在页面间反复跳转。

本需求聚焦将模型和流水线的工程产物，转化为体验人员可快速判断、复核和维护的测试资产。**不改变既有 Agent 的医学/业务判断逻辑，不改变数据库中的既有数据口径。**

## 2. 目标与非目标

### 目标

- 让体验人员在 30 秒内知道“今天要处理哪些病例、为什么要处理”。
- 让体验人员不下载文件也能阅读、判断并复核已产出的测试用例。
- 让测试资产可以按场景、旅程阶段和审核状态被高效检索和批量维护。
- 让 Prompt 发布和模型切换的影响范围清晰、可追溯。

### 非目标

- 不重做病例流水线、Agent Prompt 或六阶段旅程模型。
- 不把体验人员变成工程使用者；内部字段仍可查看，但不作为默认主界面信息。
- 本期不新增外部测试管理平台的写入集成；继续以现有导出能力为交付边界。

## 3. 用户与关键任务

| 用户 | 关键任务 | 成功标准 |
| --- | --- | --- |
| 测试体验人员 | 找到待处理病例，完成审核并导出可执行用例 | 不需要记病例 ID、Agent 编号或字段 code |
| 测试负责人 | 了解用例覆盖缺口，安排补测 | 能从覆盖空白直接进入对应资产或补测入口 |
| Prompt 维护人员 | 试跑、回归、发布或回滚版本 | 上线前的验证状态和影响范围明确 |
| 管理员 | 选择运行模型并追溯质量变化 | 知道切换是全局生效且可审计 |

## 4. 优化需求

### P0：发布前回归状态必须与实际规则一致

**问题**：当前 Prompt 页面将回归测试称为“发布前的门禁”，但草稿版本可直接发布。维护人员会误判版本已经受到发布保护。

**需求**：产品和后端规则二选一，且保持一致。

1. 推荐方案：仅当该版本最近一次回归测试全部通过时，允许发布；无回归用例的 Agent 显示“未配置门禁”，并要求显式确认。
2. 若维持当前“直接发布”策略：将所有“门禁”文案改为“推荐的发布前检查”，发布弹窗明确提示“未运行/未通过回归仍将立即生效”。
3. 每个版本在列表中展示：最近回归时间、结果、执行人、发布状态。

**验收标准**：

- 未通过回归的版本无法被误认为已通过门禁发布；或用户在发布前必须看到并确认风险。
- 已发布版本可在 10 秒内看清其最近验证结果。

### P0：阶段分析失败可局部恢复

**问题**：Agent B 阶段映射成功、Agent C 画像生成失败时，页面会已有阶段结果，但缺少“仅重试 Agent C”的明确入口。

**需求**：阶段裁定页拆分展示 B 与 C 的运行状态和最近结果，并提供“重试阶段映射”“重试画像生成”“查看运行详情”。

**验收标准**：

- B 成功、C 失败的病例，体验人员无需接口或工程协助即可重试 C。
- 重试局部步骤不会覆盖已经人工裁定的边界判断。

### P1：重构“产出”页为可阅读的测试资产预览

**问题**：当前产出页默认展示完整 JSON。该信息适合排查，不适合体验人员确认用例质量。

**需求**：

1. 默认展示“产出摘要”：已纳入用例总数、按旅程阶段/场景/真实与推测来源的分布。
2. 以用例卡片展示：测试方向、实际 query、预期要点、红线关注、关联资料、画像脚本及审核状态。
3. 原始 JSON 移到“技术详情”折叠区；下载 Excel/ZIP/JSON 按钮保持。
4. 导出前展示将导出的用例数及筛选口径。

**验收标准**：

- 体验人员无需打开 JSON，即可判断一条用例的测试目标、输入、预期结果与资料依据。
- 技术人员仍可查看和下载完整原始结构。

### P1：病例队列支持日常检索与优先级处理

**问题**：病例列表当前主要依赖病例编号；样例中患者字段为空时均显示“—”，病例积累后难以定位工作项。

**需求**：

1. 支持按病例编号、病例别名、诊断、日期搜索。
2. 增加状态筛选：待导入、待人工裁定、运行中、运行失败、已产出。
3. 列表增加“当前待办/最近失败步骤/最近更新时间”。
4. 新建病例时，除真实患者字段外，提供可选但推荐填写的非敏感“病例别名”；未填时提示以病例编号检索。

**验收标准**：

- 在 100 个病例内，可在 30 秒内定位指定病例或“所有待审核病例”。
- 队列首屏可看出下一步需要人工介入的病例。

### P1：用例审核支持批量操作，并使用业务语言

**问题**：当前仅可逐条操作；审核按钮“纳入 / 引用”不够直观，`accept`、`J05`、`SCN17` 等工程字段成为主信息。

**需求**：

1. 将审核状态的默认展示统一为“已纳入 / 未纳入”；“引用”若表示拒绝，应改为“不纳入”。
2. 支持按场景、阶段、证据来源和当前状态筛选后批量“纳入/不纳入”。
3. 批量不纳入时可选填写原因；显示“已审核 X / 共 Y 条”。
4. 默认展示业务名称，例如 `J05 · 康复随访期`、`SCN17 · 场景名称`；code 放到辅助信息或技术详情。

**验收标准**：

- 审核 30 条同类用例时，不需要逐条重复点击。
- 任意用例的审核结论在工坊、用例库和导出文件中语义一致。

### P1：资料导入前支持整理与确认

**问题**：上传后可看缩略图，但缺少清楚的删除误传文件、资料标识与“即将参与抽取的资料清单”。

**需求**：

1. 上传区显示每份资料的缩略图、文件名、序号和文件类型。
2. 在运行 Agent A 前允许删除误传资料，并支持大图预览。
3. 运行按钮旁展示“将使用 N 份资料抽取”，并在确认后提交。

**验收标准**：

- 用户可在抽取前发现并移除误传资料。
- 不会因资料数量或文件集合不明确而误触发抽取。

### P2：让覆盖空白可行动

**问题**：覆盖矩阵能够标记“0 · 空白”，但不能将空白直接转为补测工作。

**需求**：点击覆盖格后展示该场景说明、当前用例数、关联病例数，并提供：

- 跳转至已筛选的用例库；
- 跳转至适合补测的病例队列；
- 创建补测任务草稿（如本期不做任务系统，可先复制补测清单）。

**验收标准**：

- 从发现覆盖空白到打开对应候选资产不超过两次点击。

### P2：全局模型切换明确影响范围并留痕

**问题**：MiniMax/Kimi 的切换位于全局顶栏，一次点击即可影响后续所有 Agent 运行，影响范围不够显性。

**需求**：

1. 切换前二次确认，明确“影响下一次病例流水线和沙盒试跑”。
2. 切换后显示短暂成功提示和当前全局生效模型。
3. 在设置或运行记录中保留切换时间、操作人、切换前后模型。

**验收标准**：

- 使用者能明确判断某次运行使用的模型以及是否由全局切换导致。

## 5. 信息展示原则

- 默认使用业务语言；Agent 编号、字段 code、JSON、token 等放入技术详情。
- 页面优先回答“我现在要做什么、为什么、完成后会发生什么”。
- 高风险操作必须说明影响范围：发布、模型切换、重新生成并覆盖既有用例。
- 所有列表型页面提供空态、加载态、失败态和可恢复入口。

## 6. 建议实施顺序

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| 第一阶段 | 发布规则一致化、B/C 局部重试、产出页改为用例预览 | 后端发布校验与运行状态接口可能需要补充 |
| 第二阶段 | 病例检索与待办、批量审核、资料整理 | 列表筛选/批量更新接口 |
| 第三阶段 | 覆盖空白行动入口、模型切换审计 | 看板跳转参数、审计数据 |

## 7. 验收走查脚本

1. 新建一个带病例别名的病例，上传多份资料，删除其中一份误传资料后再运行抽取。
2. 构造一次 Agent C 失败，确认可以只重试 C，不重跑或覆盖已完成的 B 结果。
3. 生成至少 20 条用例，按场景筛选后批量纳入和批量不纳入；确认审核进度正确。
4. 进入产出页，在不展开 JSON 的前提下确认用例的 query、预期要点、资料证据和画像脚本。
5. 对一个未通过回归的 Prompt 草稿尝试发布，确认系统行为与页面文案一致。
6. 在覆盖矩阵点击一个空白场景，确认可直接进入对应的补测上下文。
7. 切换模型并运行一次沙盒或流水线，确认运行记录能追溯所用模型与切换信息。
